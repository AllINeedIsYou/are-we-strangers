# Контракт фронта и FastAPI

К существующему FastAPI подключены авторизация, поиск пользователей, создание и список чатов, история и отправка текстовых сообщений, доставка через WebSocket, прочтение, счётчики, редактирование, удаление, ответы, пересылки, закрепы, моменты, вопросы в будущее, главы, личные архивы и редактирование профиля. Серверные медиа ещё не подключены. Звонки и видеозвонки исключены из плана по решению пользователя 21 ноября 2026; существующие кнопки остаются в интерфейсе.

## Подключённая авторизация

Фронт обращается к `/api/auth/*` с `credentials: include`. Vite и Vite Preview проксируют `/api` на `http://127.0.0.1:8000`; другой адрес можно задать серверной переменной `AWS_API_TARGET`. В текущем локальном запуске порт 8000 занят другим проектом: Are we strangers? запущен на 8002, а игнорируемый Git файл `frontend/.env.local` задаёт `AWS_API_TARGET=http://127.0.0.1:8002`. Для опубликованного фронта нужен такой же маршрут через сервер/обратный прокси либо отдельно согласованная настройка CORS и cookie.

| Метод | Путь | Запрос и ответ |
| --- | --- | --- |
| POST | /api/auth/login | `{login, password}` → UserResponse и HttpOnly cookie `session_token` |
| GET | /api/auth/me | Cookie → UserResponse; 401 означает отсутствие действующей сессии |
| POST | /api/auth/logout | Отзыв текущей сессии и удаление cookie; 204 без тела |
| POST | /api/auth/register | `{phone, email, name, username, password}` → `{user, verification_token, verification_expires_at, telegram_url}`; вход ещё не выполнен |
| POST | /api/auth/resend-phone-verification | `{phone, password}` → новая ссылка и заявка подтверждения |
| POST | /api/auth/verify-phone | `{verification_token, code}` → UserResponse; затем отдельный вход по паролю |
| POST | /api/auth/request-email-verification | Cookie, без тела → `{expires_at}`; 409 — уже подтверждена, 429 — повторный запрос раньше минуты, 502 — ошибка отправки |
| POST | /api/auth/verify-email | `{token}` → UserResponse; подтверждение не создаёт сессию входа |
| POST | /api/auth/request-password-reset | `{email}` → 202 `{message}`; одинаковый ответ для неизвестной/неподтверждённой почты и ограничения повторного письма |
| POST | /api/auth/reset-password | `{token, new_password}` → 204 без тела, удаление cookie, отзыв сессий и закрытие WebSocket; 400 — недействительная ссылка или повтор текущего пароля |

Username при регистрации вводится после статичного `@`, отправляется без `@`, хранится сервером с `@`. Максимум 31 символ без префикса. Регистр сохраняется. Вход по username требует `@`; также доступны почта и телефон. Пароль передаётся без преобразований. Фронт не сохраняет пароли и токены входа в localStorage/sessionStorage.

Экран `/verify-email?token=...` читает токен в память и убирает его из адресной строки. Подтверждение выполняется по явному нажатию кнопки через POST, а не при открытии ссылки. Ошибки API показываются в форме; сетевой сбой не трактуется как успешный вход. Восстановление пароля подключено ниже.

На локальном HTTP существующий сервер ставит `secure=False`, срок cookie и сессии — 30 дней. Для HTTPS-публикации серверу потребуется `secure=True`. Локальная демонстрация и метаданные аватара изолированы по ID аккаунта (`aws.demo.v1.user.{id}`, `aws.avatar.user.{id}`). Текстовые данные профиля сохраняются на сервере; серверная загрузка аватара ещё не подключена.

## Подключённая переписка

| Метод | Путь | Запрос и ответ |
| --- | --- | --- |
| GET | /api/user/search?q=… | Частичный регистрозависимый поиск по `@username` или точный поиск полного телефона → массив `{id, name, username}`, максимум 20 для username |
| GET | /api/chats | Массив `{id, created_at, partner: {id, name, username}, unread_count}` |
| POST | /api/chats | `{partner_id}` → существующий или новый диалог в том же формате |
| GET | /api/chats/{chat_id}/messages?before_id=… | Последние 50 сообщений до ID, либо последние 50 без курсора; массив в хронологическом порядке |
| POST | /api/chats/{chat_id}/messages | `{text}` → сохранённое сообщение, 201 |
| POST | /api/chats/{chat_id}/read | `{message_ids: [1…100 ID]}` → `{reader_id, chat_id, message_ids}` реально изменённых сообщений |
| PATCH | /api/chats/{chat_id}/messages/{message_id} | `{text}` → MessageResponse; изменять можно своё сообщение, многократно |
| DELETE | /api/chats/{chat_id}/messages/delete | JSON `{message_ids: [1…100 ID], scope: "self"\|"everyone"}` → `{actor_id, chat_id, message_ids, scope}` |
| WS | /api/ws | Cookie `session_token`; сервер присылает `{type: "connected", user_id}`; `{type: "ping"}` → `{type: "pong"}` |

Сообщение сервера: `{id, chat_id, sender_id, text, created_at, is_read, is_edited}`. После commit сервер отправляет обоим участникам, во все их подключения, `{type: "message.created", message: MessageResponse}`. Направление сообщения выводится из `sender_id`, время и разделители дней — из `created_at`. Максимум 4096 символов; текст передаётся без обрезки и изменения форматирования, пустое по содержанию сообщение не отправляется.

Все HTTP-запросы используют `credentials: include`. WebSocket открывается на том же origin (`ws:` для HTTP, `wss:` для HTTPS), браузер передаёт cookie сам. Vite Dev и Preview проксируют `/api` с поддержкой WebSocket (`ws: true`), включая upgrade на `/api/ws`. Токены не передаются в URL или localStorage.

Поиск по имени работает только среди своих чатов, без запроса глобального поиска. При вводе `@username` или телефона показываются два раздела: «Мои чаты» и «Глобальный поиск». Username сопоставляется по префиксу с сохранением регистра. Для номера существующий диалог определяется по ID пользователя из точного результата API: публичный профиль не раскрывает телефон. Из глобальных результатов фронт исключает пользователей, с которыми уже есть чат, по partner ID. Запрос задерживается на 250 мс после ввода; предыдущие запросы отменяются, устаревшие результаты не показываются. Сам пользователь исключён из результатов. На телефоне открытие результата переводит к переписке; на компьютере переписка остаётся рядом со списком.

POST-ответ и WS-событие объединяются по серверному ID. В UI появляются только подтверждённые сервером сообщения. При ошибке текст остаётся в поле; автоматического повтора POST нет: сервер ещё не поддерживает `client_id` и идемпотентность, а при потере ответа сообщение уже могло сохраниться. Перед ручным повтором предлагается проверить историю.

При разрыве WS используется повторное подключение с задержкой 1, 2, 4, 8, максимум 15 секунд. Ping каждые 20 секунд и ожидание pong до 10 секунд позволяют обнаружить зависшее соединение. После `connected`, возврата во вкладку и восстановления сети список и история перечитываются. Для пропуска более 50 сообщений страницы загружаются назад до последней завершённой точки сверки; новые live-события не сдвигают эту точку преждевременно. Загруженный диапазон также сверяется с сервером, чтобы восстановить пропущенные правки, прочтение и удаления. Скрытые сообщения исключаются до ограничения страницы; локальные отметки удаления не дают поздним HTTP/WS-ответам вернуть их обратно. Загрузка более ранних сообщений сохраняет положение прокрутки. Полного журнала событий/replay на сервере пока нет.

При выходе или смене аккаунта соединение закрывается, запросы отменяются, поздние результаты игнорируются. HTTP 401 возвращает к входу; сбой сети сохраняет переписку и показывает ошибку. Сервер проверяет сессию при установке WS, но пока не закрывает уже открытые подключения при истечении/отзыве сессии — это отдельная задача бэка.

Список чатов сервера не содержит последнего сообщения, поэтому фронт получает последние страницы для превью (не более трёх запросов истории одновременно). Время активности собеседника неизвестно: вместо выдуманного online показывается username. Одна галочка означает «сохранено на сервере», две — `is_read=true`. Счётчики `unread_count` берутся из API. При первом видимом пикселе входящего сообщения над полем ввода счётчик уменьшается сразу, без ожидания паузы в прокрутке или HTTP-ответа. Пока запрос выполняется, старый ответ списка чатов не возвращает прежнее значение. При ошибке неподтверждённые отметки и счётчик восстанавливаются; WS/HTTP-подтверждение не вычитает сообщение второй раз. Список сохраняет порядок сервера по последнему видимому сообщению; новое входящее или своё сообщение поднимает чат, прочтение и редактирование этого не делают. Поиск внутри чата работает по загруженной истории, это явно подписано. Новые входящие события запускают уведомление звезды с cooldown 2,5 секунды; догрузка истории вспышек не вызывает.

Реальные чаты живут в памяти и загружаются из API; они не подменяются демо при ошибке. Отдельная кнопка «Демо» открывает прежний визуальный макет и локальные механики. Данные демо остаются изолированы по ID аккаунта. В реальном режиме неподключённые операции недоступны: ответ цитатой, закрепление, пересылка, моменты, главы, медиа и записи. Копирование, выбор до 100 сообщений, редактирование своего текста, удаление у себя/у обоих и поиск по загруженным сообщениям доступны. Удалять входящие у обоих также разрешает сервер. Изменения видны после подтверждения, ошибки сохраняют текст/сообщения; автоматического повтора изменений нет.

## Прочтение и события изменений

Открытие переписки не сбрасывает счётчик. Если непрочитанные не помещаются в последние 50 сообщений, фронт догружает историю до начала непрочитанных и показывает разделитель «Новые сообщения». В активной вкладке отмечаются только видимые входящие сообщения с учётом перекрывающих историю шапки и поля ввода. На телефоне закрытая переписка не читается; диалоги и профиль временно приостанавливают отметки. Повторные ID и одновременные запросы объединяются, по 100 ID максимум.

События WS: `messages.read` с `{reader_id, chat_id, message_ids}`, `message.updated` с `{message}`, `messages.deleted` с `{actor_id, chat_id, message_ids, scope}`. Прочтение синхронизирует галочки во всех подключениях. `self` удаляет только у аккаунта-инициатора, `everyone` — у обоих. Подтверждение удаления подписано «Удалить у всех». Окно закрывается сразу после нажатия. Плавная анимация начинается параллельно запросу, без ожидания HTTP-ответа; серверное подтверждение и WS-событие используют одну анимацию. При ошибке запрос отменяет визуальное удаление и восстанавливает сообщение. Восстановления уже подтверждённых серверных удалений пока нет. После повторного подключения загруженная история сверяется снова, включая сообщения, изменённые/удалённые без live-события.

## Контракт медиа

Asset: `{id, kind: photo|voice|circle|video|file, mime, size, name, duration, url}`. Сейчас `id` — ключ Blob в IndexedDB, а `url` создаётся временно и отзывается при размонтировании. После подключения API: загрузить Blob multipart, получить серверный asset_id и постоянный авторизованный URL, затем отправить сообщение с asset_ids. Нельзя пересылать blob: URL на другое устройство. Сервер проверяет действительный формат, размер, принадлежность к чату и доступ к скачиванию.

Кружок и голосовое записываются через MediaRecorder в поддерживаемом браузером WebM/Opus либо MP4/AAC; учитывать mime вместо предположения о расширении. Момент должен хранить массив снимков сообщений и ссылок на медиа. Сервер не удаляет физический файл, пока на него ссылаются моменты, пересылки или восстановимые сообщения. Удаление scope=everyone синхронизируется отдельным событием WebSocket; локальный журнал прототипа этого не делает.


Аватар пока обрезается пользователем и хранится в IndexedDB; серверной загрузки ещё нет. Уведомление ограничено кулдауном 2500 мс, который не продлевается во время частых сообщений. Анимация удаления сохраняет плавную длительность и начинается сразу; выбранный `scope` отправляется параллельно. Итоговую доставку удаления другому пользователю обеспечивает сервер.

Ширина текстового пузыря на компьютере ограничена 480 CSS-пикселями, чтобы длинный текст переносился как в Telegram. Правило действует только от 761 пикселя; размеры мобильных сообщений сохранены.

## Личный архив — подключён 21 ноября 2026

`GET /api/archive` возвращает `chat_ids`, `moment_ids`, `question_ids` текущего пользователя. Состояние хранится на сервере; локального дублирующего архива нет. Существующие списки чатов, моментов и вопросов сохраняют все записи, а интерфейс разделяет их по этим идентификаторам.

Изменение состояния — `PATCH /api/chats/{chat_id}/archive`, `PATCH /api/chats/{chat_id}/moments/{moment_id}/archive`, `PATCH /api/chats/{chat_id}/future-questions/{question_id}/archive`. Тело `{ "archived": true | false }`, ответ `{ chat_id, item_type: "chat" | "moment" | "question", item_id, archived }`, статус 200. Изменения отображаются по подтверждению HTTP или `archive.changed` в существующем WebSocket. Событие относится только к владельцу сессии. После переподключения, возвращения во вкладку и выхода устройства в сеть архив перечитывается. Запоздавшие GET/PATCH не отменяют уже полученное новое событие; после событий выполняется сверка с GET. Ошибки не запускают автоматические повторные PATCH. При выходе запросы отменяются, данные другого аккаунта не используются.

Архив чатов доступен сверху списка на ПК. На телефоне раскрывается потягиванием списка вниз у верхней границы и остаётся до входа в чат. Открытие архивного чата не разархивирует его. Действия доступны через контекстное меню строки (правый щелчок, удержание пальца, Shift+F10) и меню переписки. Чаты не удаляются. Новые сообщения не извлекают чат из архива.

В профиле → «Ваша история» → «Архив» находятся моменты и вопросы выбранного чата. У обычных карточек есть «В архив», у архивных — «Вернуть из архива». В пустом архиве — мерцающая звезда и «тут пусто», при наличии записей появляются вкладки «Моменты»/«Вопросы»; пустая вкладка показывает такую же звезду. Главы не архивируются. Архивные вопросы сохраняют время открытия и серверные правила показа ответов; их плашки скрыты из переписки до возвращения из архива. Ошибка или незавершённая загрузка показываются отдельно от пустого архива. Анимации учитывают уменьшение движения в настройках устройства.

Изменение данных профиля и восстановление/смена пароля через почту подключены ниже; смена почты через код Telegram-бота выполняется позднее. Все медиа отложены на последний этап.

У строки архива чатов счётчик показывает сумму `unread` всех архивных чатов и отсутствует при нуле. Автоматический выбор первого чата после входа учитывает архив и ждёт его загрузки: архивные сообщения не читаются из-за такого выбора. Кнопки сортировки и действия архива компактные.

При локальном архивировании момента/вопроса карточка сгорает снизу вверх; при возвращении — от центра к краям. Реальный DOM маскируется, поверх рисуются маленькие круглые красные частицы. Анимация начинается сразу, параллельно PATCH; фильтрация своей карточки откладывается до подтверждения и завершения эффекта, включая пришедшие раньше HTTP события WS/GET. Ошибка отменяет эффект и восстанавливает карточку. Более новое противоположное действие другого устройства сохраняет актуальное состояние и восстанавливает DOM. При выходе эффект отменяется; уменьшение движения отключает его. Архивирование чатов не использует эффект сгорания.

## Редактирование профиля — подключено 21 ноября 2026

В собственном профиле (кнопка профиля в нижней навигации) доступны имя, юзернейм, описание и дата рождения. В настройках убраны дублирующий переход к редактированию, проверка уведомления, вход в демо и сброс демо. `PATCH /api/user/me` с cookie принимает только изменённые поля `{name?, username?, bio?, birthday?}`. Юзернейм отправляется без `@`, дата — `YYYY-MM-DD`. Очистка описания/даты отправляет явный `null`; пропущенные поля не меняются. Ответ `200 UserResponse` обновляет аккаунт только после серверного подтверждения; повторного автоматического PATCH нет. Ошибки 409/422/сети сохраняют введённый текст, 401 завершает локальную сессию. Закрытие формы/выход отменяет ожидание ответа. Аватар остаётся локальным, телефон, почта и пароль через эту форму не меняются.

`UserResponse` и `PublicUserResponse` передают nullable `bio` и `birthday`. Публичные значения из списка чатов отображаются в карточке собеседника; дата форматируется без сдвига часового пояса. Собственный аккаунт и список чатов перечитываются при возвращении во вкладку. Старый GET аккаунта не перезаписывает результат уже завершённого сохранения. Отдельного события изменения профиля в текущем серверном WebSocket нет, поэтому мгновенное обновление профиля собеседника во всех открытых вкладках не заявляется.

Восстановление/смена пароля через почту подключены. Следующий согласованный сценарий — смена почты через код Telegram-бота. Смена телефона ещё не реализована. Медиа остаются последним этапом. Звонки и видеозвонки не разрабатываются, их кнопки сохраняются.

Настройки аккаунта разделены на раскрывающиеся группы «Почта», «Пароль» и «Телефон» с одной разделительной линией между группами. В почте — «Сменить почту» и существующее рабочее подтверждение письмом; в остальных — «Сменить пароль» и «Сменить телефон». Смена почты и телефона пока показывает пояснение о недоступности. Смена пароля открывает запрос ссылки на подтверждённую почту аккаунта. Для подтверждённой почты действие подтверждения заменяется отметкой «Почта подтверждена». Подтверждение сохраняет ограничение повторной отправки и обработку ошибок.

## Восстановление и смена пароля — подключено 21 ноября 2026

«Забыли пароль?» открывает форму почты; «Настройки → Пароль → Сменить пароль» использует ту же форму с адресом аккаунта. Для неподтверждённой почты настройки предлагают сначала подтвердить её. После 202 показывается общий текст без раскрытия наличия аккаунта и таймер повторного запроса на 60 секунд. Ошибки не стирают адрес, повторные POST автоматически не выполняются.

Ссылка `/reset-password?token=...` открывает самостоятельную страницу нового пароля и его повтора. Токен хранится в памяти, удаляется из адресной строки до фоновых запросов; документ использует `Referrer-Policy: no-referrer` через meta. Открытие страницы не меняет пароль и не использует ссылку. POST выполняется только при явном сохранении; повтор пароля проверяется на фронте, сам пароль передаётся без обрезки. Ошибки ссылки/сети оставляют форму и возможность запросить новое письмо. Отсутствие токена показывает пояснение и форму запроса ссылки. При успехе очищаются токен и поля паролей, показывается предложение войти заново; автоматического входа нет.

Разрешённая пользователем правка бэка: `authenticate_user` перечитывает пользователя с `FOR UPDATE` до проверки пароля. `login_user` удерживает блокировку до commit создания сессии и делает rollback для HTTP/SQLAlchemy ошибок. Поэтому одновременные вход и смена пароля обрабатываются последовательно. Оба порядка проверены на отдельном временном PostgreSQL; браузерный сценарий использовал реальные ручки и WebSocket с той же тестовой БД, отправка почты была подменена. Рабочая БД и реальные письма в проверках не использовались.
